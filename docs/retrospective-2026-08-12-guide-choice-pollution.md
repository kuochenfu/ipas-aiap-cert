# 回顧：學習指引參考題選項污染（2026-08-12）

## 症狀

使用者刷題到第 160 題（`junior-ai-basics-guide-q010`）時回報「D 選項讓人無法理解」、「整個頁面都很怪」。畫面上 D 選項顯示：

```
以上皆是3-221. Ans（D）解析：強化學習（Reinforcement Learning, RL）是一種機器學習方法…
```

共 1155 字。選項按鈕高 570px、整頁 4150px——因為這段文字在**選項按鈕**與**答案摘要**各出現一次。

「整個頁面都很怪」與「D 選項有問題」是同一個原因，不是兩件事。

## 根因

兩個獨立缺陷疊加，都在 `scripts/parse-core.ts`。

### 主因：題目解析器不認得答案區塊的開頭

學習指引 PDF 的版面是「10 題 → 該批的答案解析區塊 → 下一批 10 題」。原始 markdown：

```
699|（D）以上皆是          ← 題目區塊最後一行
701|## Page 28            ← 雜訊，跳過
703| 第三章 人工智慧基礎概論  ← 雜訊，跳過
704|3-22                  ← 未過濾 → 併入 D 選項
705|1. Ans（D）            ← 未辨識 → 併入 D 選項
706|解析：強化學習…          ← 之後整段全部併入 D 選項
```

第 705 行的 `1. Ans（D）` 不匹配 `guideQuestionStart`——那個 regex 有負向前瞻 `(?!Ans[（(])`，**刻意**排除答案行以免誤判為題目。但排除之後就沒有任何規則接手：它不是題目、不是選項、也不是邊界，於是走到迴圈末尾的 `target.push(line)`，被當成最末選項的跨行延續一路吞進去，直到遇到下一個章節標題才停。

諷刺的是**答案解析器本身是對的**：

```ts
if (isStudyGuideBoundary(line) || guideQuestionStart.test(line) || guideChoiceStart.test(line)) {
  current = null;  // 答案解析器知道題目與選項的開頭
}
```

只有題目解析器缺少對稱的那一半——它不知道答案區塊的開頭。

### 次因：章節頁尾未列為雜訊

`isStudyGuideNoise` 只擋純數字 `/^\d+$/`，而學習指引的頁尾是 `3-22`（第三章第 22 頁）這種 `N-NN` 格式，漏網後直接黏在最末選項或解析尾端。

## 影響範圍

比第一眼推估的大得多。原本以為只有每批最後一題（q010、q020…）中招，重跑管線後實際是**全五科 51 題**：

| 科目 | 受影響題數 |
|---|---|
| junior-ai-basics | 11 |
| junior-genai | 7 |
| senior-ai-tech | 9 |
| senior-bigdata | 11 |
| senior-ml | 13 |

**次因的影響範圍比主因更廣。** 主因只打到每批最後一題；次因打到所有「最末選項後面剛好接著換頁」的題目，包含批次中段的 q005、q015、q025——例如 `guide-q005` 的 D 選項是「迭代次數3-21」。只修主因會留下一半的髒資料。

順帶清掉的還有解析欄位尾端的頁碼（「…增強模型的泛化能力。3-63」）。

## 修正

```ts
// 1. 答案區塊開頭作為題目區塊的結束邊界
if (isStudyGuideBoundary(line) || guideAnswerStart.test(line)) {
  finish();
  continue;
}

// 2. 章節頁尾列入雜訊
/^\d+-\d+$/.test(line) ||
```

重跑 `npm run parse:papers`：題數不變（190/179/80/90/90），diff 完全對稱（65 增 65 減），變動全為移除雜訊。

驗證：新增兩則 `parse-core` 測試重現原始版面；瀏覽器複驗第 160 題 D 選項 570px → 58px、頁面總高 4150px → 1141px；最後在**線上部署版**確認第 160 與 170 題皆正常。

## 學到的事

1. **既有測試有同樣的盲點，所以一路綠燈。** `parseStudyGuide` 的既有測試資料其實也踩到這個 bug——它的 `1. Ans（B） 選項乙` 同樣被吞進 q1 的 D 選項——但測試只斷言 `prompt` 與 `explanation`，**沒有斷言 choices**，所以從來沒失敗過。解析器測試若不逐欄位斷言，等於只驗了你想到的那幾欄。

2. **對稱的解析邏輯要對稱地檢查。** 同一份文件被兩個解析器掃過（題目、答案），答案解析器知道題目的邊界，題目解析器卻不知道答案的邊界。這種「A 認得 B，B 不認得 A」的不對稱，是這類 bug 的高發區——寫的時候只想著「別把答案誤判成題目」（負向前瞻），沒想到「那被排除之後誰接手？」

3. **負向前瞻排除了一個分類，但沒指定去處。** `(?!Ans[（(])` 讓答案行不被當成題目，卻沒有任何規則承接它，於是落入 fallback 分支。排除規則應該成對出現：排除之後要明確說它屬於誰。

4. **先量測範圍再下結論。** 我在 8/10 的題庫盤點時就記錄過這個缺陷，但當時判斷是「兩題個案，另案處理」。實際跑一次全題庫掃描（找出所有超長選項）才發現是 51 題、規律是每 10 題一次。**一行掃描腳本就能把「兩題」變成「51 題」——盤點時值得順手跑。**

5. **使用者連續回報同一個 bug 的兩個實例，是因為修正還在分支上。** 第二次回報（第 170 題）其實已經在第一次的修正範圍內。這種情況要先確認「這是新問題還是未部署的舊問題」，再決定要不要重新調查——我確認過 `main` 與分支的差異後才回覆，省下一輪無謂的偵錯。
