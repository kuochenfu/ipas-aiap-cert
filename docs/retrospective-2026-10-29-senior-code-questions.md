# 專案回顧（Retrospective）— 2026-10-29：中級程式閱讀題與漏網的附圖

使用者問「中級的歷史題庫，程式題是怎麼考的？」。盤點真題回答這個問題時，順帶發現了兩件事：
新題庫完全沒有程式題，以及兩題從 2026-08-17 起就無法作答的真題。

- 規模：新增 **88 題**程式閱讀題（bigdata 47、ml 40、ai-tech 1），每題附 **1 支可執行的驗證腳本**
- 修好 **2 題**壞題（`senior-ml-114-2-q46`、`q47`），並依實際程式碼重寫兩則詳解
- 測試：595 → **598**（新增 `tests/codeQuestions.test.ts`，`tests/figures.test.ts` 多一條）
- 成本：6 個子代理，各約 14–17 萬 tokens、11–18 分鐘；PyTorch 等驗證環境約數百 MB

同日稍早的「選項長度」改題（中級新題庫 450 題、五科 generated 138 題）記在
`docs/retrospective-2026-10-28-longest-option-cue.md`，這裡不重複。

---

## 一、最重要的一課：我們量了內容，沒有量「題目長什麼樣子」

真題的科目二、科目三，每卷最後 10–12 題是程式題，約占 **22%**。本站 AI 命題的中級題庫（522 題）一題都沒有。

這個缺口在現有的任何報表上都看不到：

- 覆蓋矩陣（`npm run report:coverage`）量的是**節點 × 認知層級 × 題型原型**；
- 分布契約量的是 L1–L4、Direct Concept、跨節點；
- 2026-08-22 的再平衡更是專門為了「L4 太少」「跨節點太少」加了 215 題。

這些都是**內容**的維度。「題目附不附程式碼」是**呈現形式**的維度，從來沒有被列成一個欄位，所以不論內容的分布調得多好，
刷新題庫的人都練不到真題裡五分之一的題型。這個缺口是直接拿真題逐題對照才看出來的，任何內部指標都不會報警。

**教訓：新題庫的分布要拿真題的分布來對照，而不只是對照規格。** 規格是我們自己寫的，只會包含我們想得到的維度。
現在 `tests/codeQuestions.test.ts` 把「程式題比例 ≥20%」寫成了測試，但更一般的做法是：每次大量命題前，
先把真題依「題幹附圖／附程式／附輸出／選項是程式」分類，和題庫比一次。

## 二、守衛測試寫成了「當時看到的症狀」，而不是「那一類缺陷」

`senior-ml-114-2-q46`、`q47` 的選項是「程式碼 A」「程式碼 A、程式碼 C」，四段程式碼全在原卷截圖裡。站上看得到選項，卻無法作答。

它們漏網的過程值得記下來：

- 2026-08-17 那一輪轉錄了 42 題的附圖，其中包括**同一個題組的前一題** q45。
- 當時寫的守衛是「沒有任何題目帶著空白選項」。當時遇到的壞題確實都是選項空白，所以這條測試把**症狀**寫進去了。
- q46、q47 的選項有字，不是空白，因此通過了測試。

這類缺陷真正的定義是：**題目文字提到了某張圖或某段程式，畫面上卻沒有**。新的測試照這個定義寫：
題幹或選項出現「下圖／附圖／程式碼 A」卻沒有轉錄就失敗。暫時拿掉修補時，這條測試確實會擋下 q46、q47；
掃過全站真題，沒有其他同類題目。

**附帶發現：看不到題目時寫出來的詳解，口氣一樣篤定。** 兩題的舊詳解都是在看不到程式碼的情況下，從官方答案反推出來的。
q47 的詳解說程式碼 B、D「在資料切割或交叉驗證函數的使用上有誤」，實際原因是 `scoring="f1"` 用在 10 個類別的資料上，
每一折都評分失敗。它錯了，但讀起來和其他對的詳解沒有差別。「官方答案為…」這個開頭是這類反推詳解的徵兆，
`senior-ml` 裡還有另外 2 則用了這個句型：`114-2-q37`（同態加密，純文字題）與 `114-2-q48`（附圖已轉錄），暫未發現問題。

## 三、可執行驗證抓到的，正是 LLM 最容易寫錯的地方

這批是全站第一批「對錯可以執行出來」的 AI 命題。每題的驗證腳本都要證明：附圖輸出是真的、正解成立、**每個錯誤選項確實是錯的**。

執行結果修正了好幾個「憑知識寫一定會寫錯」的說法：

| 題目 | 原本直覺會寫的說法 | 實際執行的結果 |
|---|---|---|
| ml q160 | 學習率調高十倍，loss 會變成 nan | 只是暴增到起點的 10¹⁵ 倍，沒有變 nan（ReLU 死掉後輸出固定），解析改寫成「爆掉」 |
| ml q168 | 把 `clip_grad_value_` 放在 `backward` 之前「沒有作用」 | torch 2.5.1 會直接拋 RuntimeError，其他版本才是靜默不作用，解析兩種都寫 |
| ml q173 | 0～4 的整數標籤配 `binary_crossentropy` 會報錯 | Keras 3 照樣能跑，只是永遠預測不出類別 2～4 |
| bigdata q197 | `sm.OLS(X, y)` 引數對調，`fit()` 會失敗 | `fit()` 能跑，到取 `.pvalues` 才因形狀不符拋例外 |
| bigdata q211 | `df.corr()` 遇到文字欄位會略過 | pandas 2.x 預設 `numeric_only=False`，會拋 ValueError（1.x 才會略過） |

這些都是「程式能跑但行為和直覺不同」的細節，也正是程式題最有鑑別度的地方。如果只靠 LLM 寫、LLM 審，
這五題都會帶著錯誤的解析上線，而且八輪內容複審也不一定抓得到，因為審查者的直覺和命題者一樣。

另一個做法也值得保留：多數子代理把題目附的程式碼與輸出寫在驗證腳本裡，再由組裝腳本抽出來產生題目 JSON。
**附圖是從執行結果產生的，而不是手寫後再去比對**，所以兩者不可能漂移。

**教訓：凡是能執行的主張，就讓它執行。** 驗證腳本只管程式行為，觀念敘述與詳解仍需人工複審，
但它把「程式題最常見的瑕疵：兩段程式碼其實都能跑」整類擋掉了。

## 四、「題位表」讓分布一次到位，但合併後的序列要另外算

過去的新題庫是先命題、再量分布、不合格就補題或改題（2026-08-22 的再平衡、2026-10 的三輪改長度都是這樣）。
這次反過來：先產生題位表，每題的 id、節點、考法、認知層級、正解字母、是否跨節點、產業情境都事先指定，子代理只負責填內容。

結果：節點配額、方案 C 的認知層級分布、跨節點比例、正解字母分布，**第一次合併就全部通過**，只有兩類例外：

1. **正解字母的週期規律**：題位表在每一批內是隨機的，但測試檢查的是「每個節點內、新舊題合併後」的序列。
   三個節點因此出現 p=5、p=6 的週期（例如每隔 6 題都是 C），各換一題的字母才解決。
   下次產生題位表時，應該把該節點既有的正解序列接在前面一起模擬。
2. **貼著邊界的契約**：senior-ai-tech 的 L3 原本是 33.1%（下限 33%），只多 1 題 L2 就掉到 32.9%。
   中級三科的 L2、L3 都貼著方案 C 的邊界，**任何加題都要先算過**；這次的題位表有算 bigdata 和 ml，漏算了只有 1 題的 ai-tech。

換字母時，ml q168 的驗證腳本用 "A"／"C" 標記各選項的寫法，所以腳本也要同步互換。
**驗證腳本也是會受「重新配置正解字母」影響的東西**，CLAUDE.md 列的三個要同步的地方（選項解析的鍵、干擾類型的鍵、詳解裡的指名字母），現在多了第四個。

## 五、新的長度線索：正解偏向中間

前三輪學到「正解不能最長」，子代理這次也確實避開了：88 題中正解最長只有 14%。但正解**最短**的也只有 8%，
正解大多落在中間長度。「去掉最長與最短、在中間兩個猜」約可拿 39 分。

這還遠不到及格，併入整科新題庫後也被稀釋了（整科只挑最長為 23–31 分），所以暫不處理。
但它說明了一件事：**只給「上限」的長度規則，會把分布推到另一個不自然的形狀。** 下次的規則應該是「正解在四個長度名次上大致均勻」，
各名次約 25%，而不是只限制最長與最短。

## 流程（可重複使用）

1. 盤點真題的題型與比例 → 計畫文件（`docs/superpowers/plans/2026-10-29-senior-code-reading-questions.md`）。
2. 以 `uv` 建立固定版本的 Python 環境（`scripts/code-questions/requirements.txt`）。
3. 產生題位表（含正解字母）；**先把各節點既有的正解序列接上去模擬週期與區塊規律**，並重算各科的分布契約。
4. 子代理依題位表命題，產出題目 JSON 與每題的驗證腳本，以 check.py 自我驗收（格式、題位、長度、簡體字、「選項 X」只指正解、執行全部腳本）。
5. 主流程抽查子代理點名的題目 → 轉成 `.code.ts` → 配額與測試 → `npm run build`、`npm run test`、`scripts/code-questions/run.sh`。
