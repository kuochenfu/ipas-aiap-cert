# 初級兩科原題庫的詳解與選項解析全面改寫 — 設計

日期：2026-08-14
範圍：`junior-ai-basics`（190 題真題）、`junior-genai`（179 題真題），共 369 題。`gen-*` 的 100 題不動。

## 問題

使用者回報原刷題區「有些題目說明得並不好」。量測後發現兩個結構性問題，都不是個別題目寫得差：

**選項解析大多根本不存在。** 目前的選項解析不是手寫的，而是拿選項文字去比對一份 106 條的詞彙表（`src/data/glossary.ts`）自動組出來。這只在選項是單純名詞時有效；真題多為情境題、選項是整句敘述，比對不到就什麼都不顯示。

| | junior-ai-basics | junior-genai |
|---|---|---|
| 自帶手寫選項解析（`gen-*`） | 50 | 50 |
| 詞彙表可組出完整四個 | 20 | 1 |
| 只組得出部分 | 16 | 4 |
| **完全沒有選項解析** | **136（61%）** | **158（74%）** |

即使組得出來，句型也是固定模板：「X：用途（例如：A、B）。本題情境指向「Y」，故不選 C。」——它解釋的是**名詞本身**，不是**這個選項在這一題為什麼錯**。

**115-2 的 100 題詳解是樣板產生的。** `resolveExplanations.ts` 的 `buildFallbackExplanation` 在找不到手寫詳解且題目本身無解析時，會用題目文字重排出一段話：

> 依學習指引中「人工智慧基礎概念…」相關概念判斷，正解為 B「…」，因為它最貼近題幹要求的任務、限制或判斷標準。A「…」較像是在問該選項本身代表的概念或應用情境時才適用；…

零資訊量。兩科的 115-2 各 50 題全數如此。

其餘題目的詳解來自手寫（115-1、114-4 各 50 題）或官方學習指引的解析區塊（guide 批），品質參差：junior-ai-basics 有 20 題、junior-genai 有 15 題短於 60 字。

## 目標

369 題的詳解全部達到同一個標準，且每題都有三個錯誤選項的逐項解析。

## 非目標

- 不動 `gen-*` 的 100 題（使用者指定；其詳解與選項解析本就逐題手寫，風格與新標準相近）。
- 不動中級三科的內容（已量測：中級三科**零題**依賴樣板產生器，刪除該機制不影響它們）。
- 不動 `past-exams/*.json`、不重跑解析管線。

## 詳解標準

每則詳解要做到四件事，順序不拘：

1. **說明正解為何成立** — 講概念或機制，不是把選項文字換句話說。
2. **點出題幹裡的決定性線索** — 是哪一句話讓答案只能是這個。
3. **處理最誘人的錯誤選項** — 通常是相鄰概念，說清楚差在哪。
4. **長度足以教會人** — 約 80–150 字。

不合格的樣態：只重述答案、只說「因為最符合題意」、通篇是題目文字重排、殘留樣板句型。

**選項解析**：一句話講「這個選項**在這一題**為什麼錯」，不是這個名詞的通用定義。這是舊詞彙表機制最大的毛病。

**既有內容的處理原則：不合標才改，合標的保留。** 115-1 與 114-4 的 200 題現有詳解品質不差，要改善而非重寫一遍。官方學習指引來的 69 題（guide 批）依使用者決定一視同仁——不合標就重寫，代價是失去「這是官方說法」的出處。

## 要刪除的機制

| 檔案／函式 | 理由 |
|---|---|
| `src/data/glossary.ts` | 詞彙表組合機制的資料來源，全面手寫後不再需要 |
| `src/data/choiceAnalysis.ts` | 詞彙表組合器 |
| `resolveExplanations.ts` 的 `buildFallbackExplanation` | 產生零資訊量的樣板詳解 |
| `resolveExplanations.ts` 的 `buildChoiceExplanations` | 產生樣板選項解析 |
| `src/ui/render.ts` 對 `composeGlossaryAnalysis` 的兩處呼叫 | 改為只讀資料層的手寫內容 |
| `tests/choiceAnalysis.test.ts` | 測試已刪除的機制 |

刪除 `glossary.ts` 同時清掉 auto-memory 中「103 條 glossary 待複審」的技術債。

## 資料層

`src/data/explanations/<subjectId>.ts` 由 `Record<string, string>` 改為：

```ts
export type QuestionExplanation = {
  explanation: string;
  /** 恰好三個錯誤選項的解析；不含正解的 key */
  choices: Partial<Record<"A" | "B" | "C" | "D", string>>;
};

export const explanations: Record<string, QuestionExplanation> = { ... };
```

中級三科同步改型別、內容照搬（`choices` 為空物件），維持型別一致。

`resolveExplanations.ts` 精簡為單一職責：把手寫內容套到對應 id 的題目上。**重跑 `npm run parse:papers` 仍只覆寫 `past-exams/*.json`、不動手寫內容** — 此既有不變式不變。

## 測試

- 每題真題有非空詳解。
- **不得殘留樣板句型**：出現「依學習指引中」或「較像是在問該選項本身代表的概念」即失敗。
- 每題恰好三個錯誤選項的解析（不含正解的 key），皆非空。
- 詳解長度 ≥60 字，落實「足以教會人」。
- 繁體中文檢查（沿用 `tests/practiceBank.test.ts` 的簡體字掃描）。
- **`gen-*` 的 100 題內容 byte-identical**，防止批次作業誤改到指定不動的部分。
- 既有測試維持通過；`getQuestions` 回傳題數不變（222／213）。

## 風險

- **最嚴重的失敗模式是「改詳解時把正解講反」** — 相當於新題庫那次「調措辭把假話改成真話」的對應風險。每批必須逐題驗證詳解論證的選項與 `answer` 一致。
- 369 題全為 LLM 產出或改寫，需人工事實查核；記錄於 `docs/coverage/` 與 auto-memory。
- 重寫 guide 批會失去官方解析的出處，此為使用者明示接受的取捨。
